# Architecture

```
Browser (static site, no keys)
   │  POST JSON (CORS-restricted, rate-limited, validated)
   ▼
Supabase Edge Functions ──► Postgres (source of truth, RLS on every table)
   │       record + outbox event written in ONE transaction
   │
   │  dispatch: immediately (best effort) + pg_cron every minute (retries)
   ▼
n8n webhooks (header auth) ──► claim event (idempotency) ──► SMTP (Hostinger) ──► inboxes
   │                                                              │
   └──────────── report result per email (callback secret) ◄──────┘
```

## Database

| Table | Purpose |
|---|---|
| `newsletter_subscribers` | email (unique), first name, status `pending/active/unsubscribed/bounced/suppressed`, consent text + time, confirmed/unsubscribed times, source, tags |
| `newsletter_tokens` | confirmation token **hashes**, expiry, `used_at` (single use) |
| `saas_products` | slug, name, description, status (`waitlist_open`/`beta` accept registrations) |
| `waitlist_registrations` | product + email unique; status `waiting → invited_early_access → invited_beta → converted / removed`; per-email delivery status |
| `contact_submissions` | enquiry + workflow status (`new/in_progress/replied/closed/spam`) + notification/acknowledgement delivery status |
| `automation_events` | outbox: type, idempotency key, status, attempts, backoff, errors |
| `email_deliveries` | one row per email per event: `pending → dispatched → smtp_accepted / failed` |
| `newsletter_campaigns`, `campaign_recipients` | campaigns, audience snapshot, per-recipient status |
| `rate_limits` | salted IP-hash counters (purged after 2 days) |
| `admin_users` | future admin dashboard access (Supabase Auth user ids) |

### Status meanings (never overstated)
- **Saved:** the row exists in its table.
- **Dispatched** (`automation_events.status = dispatched`): n8n's webhook accepted the event. This is *not* proof an email was sent.
- **smtp_accepted** (`email_deliveries.status`): Hostinger's SMTP server accepted the message. This is *not* proof it reached the inbox.
- **delivered / bounced:** reserved for future delivery or bounce reports. `public.mark_email_bounced(email)` and the callback action `email.bounced` are ready for a bounce-mailbox workflow.
- **failed:** with the SMTP or HTTP error in `error` / `last_error`.

### Event lifecycle
`pending → dispatching → dispatched → processing (claimed by n8n) → completed`

On a webhook error or SMTP failure the event goes to `failed` and is retried with exponential backoff (1, 2, 4 … minutes, capped at 3 h, max 8 attempts). After that it becomes `dead`. A retry resends **only the emails not yet accepted**. Events stuck mid-flight for more than 30 minutes are re-dispatched. Duplicate webhook deliveries are refused at the claim step.

## Adding a new SaaS product
1. Add it to `products` in `site.config.mjs` (set `featured: true` to show it on the home page).
2. `npm run products:sql` → run the SQL in Supabase.
3. Rebuild and deploy. The product gets `/waitlist/<slug>/` and the same form, backend and emails, automatically personalised.

Future early-access, beta and launch emails: select registrations by `product_id` and `status = 'waiting'`, then update `status` as people are invited. The campaign tables and workflow E are the model for this.

## Sending a newsletter campaign
```sql
insert into newsletter_campaigns (identifier, subject, preheader, html_body, text_body, segment) values (
  'issue-1', 'What I''m building this month', 'A short update',
  '<p>Hi {{first_name_or_there}},</p><p>…</p>',
  'Hi {{first_name_or_there}},\n\n…',
  '{}'   -- or '{"tags_any":["founders"]}' / '{"sources_any":["website"]}'
);
select public.request_campaign_send('issue-1');
```
Only `active` subscribers are included, and each one is re-checked right before sending. Track progress with:
```sql
select status, count(*) from campaign_recipients r join newsletter_campaigns c on c.id = r.campaign_id
where c.identifier = 'issue-1' group by 1;
```

## Privacy operations (run in the SQL editor)
```sql
select public.export_personal_data('person@example.com');   -- access request
select public.delete_personal_data('person@example.com');   -- erasure request
```
`purge_expired_data()` runs daily: it deletes rate-limit rows after 2 days, expired tokens after 30 days, and never-confirmed subscribers after 30 days.

## Future admin dashboard
The groundwork is in place: RLS policies give users listed in `admin_users` read access to all tables, plus `status` updates on enquiries and registrations. A dashboard can therefore use Supabase Auth + the publishable key safely, without any service key in the browser. To enable it:
```sql
insert into admin_users (user_id) values ('<your auth.users id>');
```
Useful queries for a first version: subscriber counts by status, `automation_events where status in ('failed','dead')`, `email_deliveries where status = 'failed'`, and registrations per product. Campaign triggering should go through a new authenticated Edge Function that calls `request_campaign_send`.
